# Financial Report RAG System — Data-First Design

## 1. Objective

Build a reproducible, resume-ready financial-report RAG system in two to three days. The first priority is to produce defensible experimental results from FinQA; API packaging, GitHub presentation, and interview-learning material follow after the results are verified.

Every number used on the resume must be generated by a committed evaluation command and preserved in machine-readable result files. No target improvement is assumed in advance.

## 2. Success Criteria

The project is complete only when all of the following are true:

1. FinQA train, development, and test splits are loaded reproducibly, with the test split excluded from tuning.
2. BM25, dense, hybrid, and hybrid-plus-reranker retrieval are evaluated using identical held-out queries.
3. Recall@5, MRR, NDCG@5, query count, and latency are written to versioned JSON results.
4. A controlled numerical-execution experiment compares direct LLM calculation with Python execution on the same FinQA evidence and symbolic programs.
5. Numerical exact match, arithmetic error rate, relative error reduction, query count, and latency are saved with per-query predictions.
6. A FastAPI service exposes health, question-answering, and metrics endpoints with validated JSON schemas and source citations.
7. Unit tests cover parsing, retrieval metrics, rank fusion, numerical execution, and API validation; a smoke evaluation covers the complete pipeline.
8. The README contains reproducible commands, architecture, results, examples, limitations, and an honest resume-bullet section generated from the saved metrics.
9. A short interview guide explains the architecture, metrics, design trade-offs, common failure modes, and the exact origin of every resume number.

## 3. Scope

### Included

- FinQA's prepared English financial-report text, tables, questions, gold evidence, answers, and symbolic programs.
- Evidence-unit parsing for report sentences and table rows.
- BM25 lexical retrieval.
- Dense retrieval using a small English sentence-transformer suitable for local inference.
- Reciprocal-rank fusion of BM25 and dense rankings.
- Cross-encoder reranking of the fused candidate set.
- Text and table source citations.
- A controlled numerical-execution comparison using the official `Qwen/Qwen3-4B-Instruct-2507` model and a deterministic Python calculator.
- Offline evaluation, FastAPI serving, tests, and GitHub documentation.

### Deferred

- Raw annual-report PDF parsing and OCR.
- QLoRA fine-tuning; this belongs to the separate second project.
- Multi-user authentication, cloud production deployment, and a polished web UI.
- Claims that the project was completed during the 2025 Huatai Securities internship.

The deferred items are not needed to obtain defensible project-one metrics or to demonstrate the intended RAG architecture.

## 4. Data and Leakage Control

The official FinQA repository is the source of record. Each report is converted into evidence units with stable identifiers:

- narrative sentences from `pre_text` and `post_text`;
- table rows serialized with their column headers;
- metadata containing split, report identifier, evidence identifier, and evidence type.

Development data is used for choosing chunk representation, candidate count, fusion weights, and reranker depth. Test data is evaluated once after those choices are fixed. The result manifest records the source revision or file checksums, split, random seed, query count, model identifiers, and all retrieval parameters.

Gold evidence labels are matched to normalized evidence identifiers. Unmatched labels are reported explicitly rather than silently discarded.

## 5. Retrieval Pipeline

All retrieval configurations operate over the same report-local candidate evidence so comparisons remain fair.

1. **BM25 baseline:** tokenize the English query and evidence units; rank by BM25 score.
2. **Dense baseline:** embed the same query and evidence units; rank by cosine similarity.
3. **Hybrid retrieval:** retrieve the top candidates from BM25 and dense retrieval, then combine rankings with reciprocal-rank fusion.
4. **Hybrid plus reranker:** score the fused candidates with a cross-encoder and return the final top five.

Development-set experiments select the candidate depth and fusion settings. The test evaluation reports every configuration, even if the hybrid system does not outperform a baseline.

### Retrieval Metrics

- **Recall@5:** mean fraction of each query's gold evidence units appearing in the top five.
- **Hit@5:** fraction of queries with at least one gold evidence unit in the top five.
- **MRR:** mean reciprocal rank of the first gold evidence unit.
- **NDCG@5:** ranking quality with binary gold-evidence relevance.
- **Latency:** per-query P50 and P95 retrieval latency measured after warm-up.

The resume may say “improved Recall@5 from A to B” only if the selected hybrid configuration produces a real test-set improvement. Otherwise it will say “benchmarked” and describe the measured trade-off.

## 6. Numerical-Execution Experiment

The numerical comparison isolates arithmetic execution from evidence retrieval and program prediction so that the claimed reduction in arithmetic errors is interpretable.

For each eligible held-out FinQA numerical question:

1. Provide the same gold evidence and symbolic operation program to both conditions.
2. In the **direct-LLM condition**, ask `Qwen/Qwen3-4B-Instruct-2507` to calculate and return the final answer.
3. In the **tool condition**, execute the symbolic program with a whitelisted deterministic Python calculator and return the result.
4. Normalize percentages, currency symbols, commas, signs, and rounding consistently before comparison with the gold answer.

This controlled study measures the arithmetic stage only and will be described as such in the README. A separate end-to-end example demonstrates retrieval, routing, calculation, and citation, but no end-to-end accuracy claim will be substituted for the controlled result.

### Numerical Metrics

- normalized exact-match accuracy;
- arithmetic error rate;
- relative error reduction: `(direct_error_rate - tool_error_rate) / direct_error_rate`;
- absolute error-rate reduction in percentage points;
- P50 and P95 execution latency;
- per-query error category and raw output.

If the direct model has zero arithmetic errors on the evaluated set, relative reduction is undefined and will not be claimed. The report will use exact match and absolute differences instead.

## 7. Application Architecture

The codebase is split into small, independently testable modules:

- `data`: download verification, FinQA parsing, normalization, and evidence identifiers;
- `retrieval`: BM25, dense retrieval, reciprocal-rank fusion, and cross-encoder reranking;
- `reasoning`: query routing, safe FinQA program parsing, and deterministic calculation;
- `generation`: configurable local Qwen inference and cited response formatting;
- `evaluation`: retrieval metrics, numerical metrics, latency measurement, manifests, and prediction logging;
- `api`: FastAPI schemas and endpoints;
- `cli`: reproducible data preparation, evaluation, and serving commands.

The online flow is:

`question -> report evidence -> BM25 + dense -> rank fusion -> reranker -> router -> text answer or calculator -> answer + citations`

The evaluator calls the same modules used by the API so offline metrics and the demonstration service cannot silently diverge.

## 8. Interfaces and Artifacts

The primary commands will support:

- preparing and validating FinQA data;
- running a small smoke evaluation;
- running development retrieval experiments;
- running the locked test evaluation;
- running the numerical comparison;
- starting the FastAPI service;
- running the automated tests.

Generated files are separated from source code and include:

- `artifacts/retrieval/metrics_summary.json`;
- `artifacts/retrieval/predictions.jsonl`;
- `artifacts/numerical/metrics_summary.json`;
- `artifacts/numerical/predictions.jsonl`;
- `artifacts/experiment_manifest.json`;
- a Markdown results table generated from those JSON files.

The API returns a structured answer, route, confidence or score information where available, evidence identifiers, source text or table rows, and latency.

## 9. Error Handling and Safety

- Data checks fail with a clear message when required FinQA fields or gold evidence labels are missing.
- Model download and GPU failures produce actionable diagnostics; retrieval evaluation remains runnable on CPU.
- The numerical executor accepts only a fixed FinQA operation grammar and numeric operands. It does not execute arbitrary model-generated Python.
- Division by zero, invalid references, unsupported operations, and non-finite results are captured as structured errors.
- Partial experiments write to temporary result names and are promoted only after successful completion, preventing incomplete files from being mistaken for final metrics.

## 10. Verification Strategy

Unit tests use small committed fixtures and do not require model downloads. Integration tests validate a miniature end-to-end retrieval and calculation flow. A smoke run uses a small FinQA subset before any full evaluation.

Before results are used on the resume:

1. run the locked evaluation command twice with the same seed;
2. confirm identical rankings and metrics within documented numerical tolerances;
3. inspect a sample of successful and failed predictions;
4. verify that result counts match the manifest;
5. generate the resume bullet directly from the verified summary file;
6. record any limitations, sampling decisions, or failed improvement hypotheses.

## 11. Delivery Order

1. Establish the environment, data fixture, and tests.
2. Implement the FinQA parser and retrieval metrics.
3. Produce the BM25 baseline immediately.
4. Add dense retrieval, hybrid fusion, and reranking; lock development choices and run the test evaluation.
5. Run the numerical direct-LLM versus Python-execution experiment.
6. Freeze the verified resume metrics and draft the resume bullets.

This order intentionally produces defensible resume data before presentation work without weakening reproducibility or changing the final project scope.
